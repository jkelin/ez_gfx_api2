# ez-gfx-compiler

Shader compiler library and offline `clap` CLI using `shader-slang` in-process sessions. They emit format-v5 `.ezgfxshader` artifacts containing selected SPIR-V, DXIL, and/or Metal products for every discovered `(stage, entry-point name)`, canonical reflection including fixed compute workgroup dimensions, provenance, and target-specific compatibility. Apple hosts always finish Metal products as runtime-loadable metallib, including development requests; non-Apple development builds retain MSL for cross-target validation only. Metallib builds record macOS platform, architecture, deployment minimum, SDK, Metal language, metallib contract, and Apple toolchain identity.

`EasyGraphicsCompiler::compile_shader(source, targets, development)` accepts a `.slang` root source path, any nonempty subset of the `spirv`, `dxil`, and `metal` target families, and a development-mode flag. It discovers every entry point, including multiple names in one stage, and compiles each for every selected target. Target order is normalized. The method returns a validated host-side `CompiledShader`; `save_shader` serializes it, while `EasyGraphicsCompiler::load_compiled_shader` validates existing bytes. Exact stage/name loading occurs through a runtime context and returns owning stage-typed handles. The CLI applies the same contract and writes `<source-stem>.ezgfxshader` unless `--output` is supplied.

Compiler and build environments require the native Slang shared library. `shader-slang` discovers a Vulkan SDK installation or `SLANG_DIR`/`SLANG_LIB_DIR`; DXIL additionally requires `dxil.dll` and `dxcompiler.dll`. Runtime packages depend on `ez-gfx-artifact`, not this crate or native compiler libraries.
